# Technical choices

The technical choices of the [roadmap](../roadmap.md), with their reasons. A project made from the template confirms each one at its start, and records here the choices of its own.

| Topic | Choice | Reason |
|---|---|---|
| Template | [rust-desktop-template](https://github.com/sylent-dev/rust-desktop-template) at `6e0625e`, taken on 2026-11-15 (step 0b) | The project started from rust-cli-template at `32e9ad4`, then moved to a window. The next update from the template takes the delta from `6e0625e` only. |
| License | GPL-3.0-or-later, in `LICENSE` | Chosen by the owner on 2026-11-15, like rust-exile-market: the application will ship assets of its own, and a published fork must give its code back. Replaces MIT, chosen at the setup: the code published under MIT until then was the starting point of the template only. The assets get a license of their own when they come (an icon or a font under its license, listed in the archives: `docs/releases.md`). |
| Interface | `egui` and `eframe`, with the `glow` renderer (OpenGL) | Chosen by the owner on 2026-11-14, like rust-exile-market: pure Rust, one executable per system without a web engine, and an interface that is a function of the state, drawn again at each frame, which a learner can follow from top to bottom. A window reaches the public of the owner's portfolio, who don't use a terminal. `glow` rather than `wgpu`: a smaller executable and a faster build, enough for a 2D interface. Replaces `ratatui` with `crossterm`, chosen the same day: lighter, but a terminal interface suits few of the people who track their subscriptions. |
| Linux display | X11 always (XWayland under Wayland), chosen in `main.rs` | The same behavior on every Linux desktop: under Wayland, a window can't place itself, nor read the position eframe restores at the next launch. Change it if the application needs Wayland itself (fractional scaling, no XWayland on the desktop). |
| Window title bar | The title bar of the system | The template's default. Decided in the first wireframes: keep it, or draw its own (`with_decorations(false)`, and its buttons from the start). |
| Translations | Fluent (`fluent-bundle`) read directly, one `.ftl` file per language in `locales/`, embedded in the executable | Plurals and genders written by the translators, without code. Rather than `i18n-embed` and its `fl!` macro, which generates code a reader can't see (owner, 2026-11-14): the code names a message by a variant of `Message` or by a method of `Translator` (`src/i18n.rs`), never by a string, and a test checks that the code and every file have the same messages. |
| Interface language | The language of the system (`sys-locale`) until the user picks one in the settings | English when the system's language isn't translated. |
| Settings | TOML in the configuration directory of the user (`directories`), written atomically (a new file synced, then renamed); the size and position of the window kept by eframe in `window.ron` next to it | Readable and editable by hand. A value this version can't read takes its default without losing the others; a file that isn't TOML is kept aside (`settings.invalid.toml`) before the defaults replace it. |
| Log | `simplelog` to the standard error and to a file in the local data directory: `log.txt` for the window, written again at each launch; `check-log.txt` for the daily check, added to and cut to its last 500 lines | A release on Windows has no console. Two files, so that a check run while the window is open never erases its log, and the window never erases the history of the checks (step 1a). |
| Daily check | One executable: started with the argument `--check` (read from `std::env::args`, without a parser of arguments), it runs the check and exits without opening a window | A single file to unpack and to update; the scheduler starts the same version as the window. A second executable would double the archives and could fall out of step with the window. |
| System scheduler | Linux: a systemd user timer (`OnCalendar` at 9:00, `Persistent=true`, which starts a missed check when the session starts again), its two files written by the window, then `systemctl --user daemon-reload` and `enable --now`. Windows: a task created by `schtasks.exe /Create /XML` (a daily trigger at 9:00, a trigger at the logon, `StartWhenAvailable`), started without a console window | The tools the systems ship, run with `std::process::Command`, rather than a crate: what is installed can be read and removed by hand, and a learner sees the real files. Rejected: an autostart entry run at each login, which misses the days the computer stays on. Critical code: its model is Fable 5.2 (roadmap). |
| Desktop notifications | `notify-rust`: the freedesktop notifications through D-Bus (`zbus`, which `accesskit` already brings) on Linux, the notifications of Windows through WinRT | One API for both systems, without `unsafe` in the application. On Windows, a notification needs the id of an installed application (an AppUserModelID): without an installer, version 1 uses the id of PowerShell, the default of `notify-rust`, and the notification shows « Windows PowerShell » as its sender. An id of its own, registered for the user, waits in the backlog, to try with a tester. `notify-rust` 4.19 brings `zbus` 6, `accesskit` `zbus` 5: the build step looks for a version that shares one, or accepts both. |
| Dates | `jiff`: the calendar dates (`civil::Date`), the months added with the last day of a shorter month (31 January plus one month gives 28 February), and today's date in the time zone of the system (its database bundled on Windows) | The computation of the deadlines is critical: a tested library rather than a calendar written by hand. Tried on 2026-11-19 on the examples of `specs.md` (Deadlines). `chrono` would do too; `jiff` has one type per kind of date, which reads more easily. |
| Amounts | Read from a string (`"13.49"`) into an integer number of cents, by the application | Exact, without the rounding of floating-point numbers, nor a crate of decimal numbers for additions and divisions by 3 or 12. Two decimals at most, which every currency of the users has (a currency without decimals writes `"1200"`). |
| Data file | `subscriptions.toml`, read into the types of the application with `serde`, and changed with `toml_edit` (already in the dependency tree), which edits only the entries changed | The user may edit the file by hand: a change made in the window keeps their comments, their order and the fields a later version wrote. Rejected: CSV, which has no lists (the reminders) nor comments, and doesn't say which column is which once edited by hand. |
| Calendar export | The `.ics` file written by the application to the downloads folder of the user (`directories`, `UserDirs`), without a file dialog; one event and its alarms per deadline of the next year, without a rule of repetition (`RRULE`) | The format (RFC 5545) is a few lines of text: a crate wouldn't save code, and a learner reads the file the code writes. A dialog would bring a crate (`rfd`) and GTK or a portal client on Linux. The calendars don't all count the end of the months like the application (a rule « every month on the 31st » skips the shorter months), and the notice shifts the dates: single events keep the deadlines exactly those of the window (step 1b). |
| Second window | Allowed: each window reads the data file again before each save and when it gets the focus back, compares the entry of the subscription it changes with the one it read when its form opened, and writes its change into the fresh content | The same guard covers a second window and an edit by hand while the window is open. Rejected: a single instance that brings the first window forward, which needs the two processes to talk to each other and a window raised on X11, for a rare case (step 1b). The entries are compared by content, not by the date of change of the file, whose precision varies between systems. |
| Links and folders opened | `xdg-open` on Linux, `explorer.exe` on Windows, started with `std::process::Command`, only for an address that starts with `https://` or `http://` or for a folder of the application | The tools the systems ship, without a crate; the check of the address keeps a data file edited by hand from starting a program (step 1b). Confirmed at the build. |
| Date entry | Decided at the mock-up | The date picker of `egui_extras` needs `chrono`, a second library of dates next to `jiff`: weigh it against a field typed and checked by the application. |
| PWA | Set aside (owner, 2026-11-18) | Its notifications, when it is closed, need a push server, against « local only », and it would leave Rust. The `.ics` export brings the deadlines to the phone without a server. |
| Releases | GitHub Actions workflow triggered by version tags, from a commit of `main` only, for Linux and Windows | Builds each system on its own runner, checks the advisories and the licenses (`cargo-deny`), writes the licenses of the dependencies (`cargo-about`) and publishes the archives with `gh release`, without extra tooling. Linux and Windows chosen by the owner on 2026-11-14, so that the tool can be downloaded from their portfolio; macOS waits in the backlog, its Clippy job kept in the CI (owner, 2026-11-15). |
| Rust version | Pinned in `rust-toolchain.toml`, raised by Dependabot | A release is built by the compiler its checks ran with. |
| Actions | Each one pinned to a commit, its version in a comment | A tag can be moved by the owner of the action to another code; `.github/scripts/pinned-actions.sh` fails the CI otherwise. |
| Mock-up server | `python3 docs/mockups/serve.py <port>`, port `8753` | Serves the mock-up of the window without cache, on a port of its own (8753, unused by the other projects of the owner), so that two projects never take each other's server over. |
