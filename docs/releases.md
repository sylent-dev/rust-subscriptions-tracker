# Releases

## Publish a version

1. Run the `security-auditor` subagent on `main` and fix the findings the owner approves (a critical or high one blocks the release), and run the guides of `docs/tests/` again, if any.
2. Update `version` in `Cargo.toml` (then run `cargo build` to update `Cargo.lock`), write the notes of the version in `docs/release-notes/v<version>.md` (for the users: the download, what changed, the known limits), and merge them into `main`.
3. Check the addresses the executable is built with: `gh repo view --json nameWithOwner` gives the owner and the name of the repository of today, and a search of the code and the docs (`git grep -n '<owner>/'`) finds a link left on an old name. GitHub redirects a renamed account or repository, but an executable keeps the addresses it was built with, and the redirects stop as soon as someone claims the old name.
4. Run the Release workflow by hand on `main` (Actions, Release, Run workflow) and wait for its builds on every system: a tag can't be moved, so a build that fails at the tag costs a version number.
5. Tag the merged commit with the same version and push the tag:

   ```sh
   git switch main && git pull
   git tag v0.1.0
   git push origin v0.1.0
   ```

The [Release workflow](../.github/workflows/release.yml) builds the archives for Linux and Windows (macOS waits in the backlog) and publishes them as a GitHub release, with their checksums (`SHA256SUMS.txt`) and the notes of `docs/release-notes/<tag>.md`. The release is a normal one, never a pre-release: `releases/latest`, which a download page links to, skips the pre-releases. It fails if the tag does not match the version of `Cargo.toml`, if the notes of the version are missing, if its commit isn't on `main` (a commit that went through a pull request and its checks; a guard against a tag put by mistake, since the workflow that runs is the one of the tagged commit), or if a security advisory on a dependency isn't sorted yet (`cargo deny check advisories`: update the dependency, or list the advisory in `deny.toml` with its reason). Add a ruleset that keeps the tags `v*` from being moved or deleted (**Settings › Rules › Rulesets**, target the tags `v*`, restrict updates and deletions): a wrong tag is replaced by the next version, never pushed again.

The version of Rust is pinned in `rust-toolchain.toml`: the release is built by the compiler the checks of `main` ran with. Dependabot proposes the new versions; each action of the workflows is pinned to a commit the same way (`.github/scripts/pinned-actions.sh`, run by the CI).

Between two releases, the [Advisories workflow](../.github/workflows/advisories.yml) checks the advisories every day and fails, with an email to the owner, on a new one: a flaw that reaches the users calls for an urgent fix and a patch release.

## What an archive holds

Each archive keeps its name from one version to the next (`<executable>-windows-x64.zip`, `<executable>-linux-x64.tar.gz`), and so does the folder inside it: a download page that links to `releases/latest/download/<archive>` breaks when it is renamed.

- the executable (`<executable>` or `<executable>.exe`, the `[[bin]]` of `Cargo.toml`) and `README.md`;
- `LICENSE`, the GNU General Public License, version 3 or later, the license of the application;
- `THIRD-PARTY-LICENSES`, the licenses of the libraries built into the executable, generated by `cargo-about` (`about.toml`, `about.hbs`).

A file the executable embeds under another license (a font, icons) adds its notice to the `Package` step of the workflow, and to its `paths`, so that a rename fails on the pull request rather than at the tag.

The Linux executable is built against glibc on the oldest Ubuntu runner, not musl: it loads the graphics libraries of the system (OpenGL, X11), which a static musl executable can't. It runs on the distributions with that glibc or a newer one.

## The licenses of the dependencies

The workflow runs `cargo deny check licenses` first (`deny.toml`), and `cargo about` refuses the same licenses (`accepted` in `about.toml`, kept the same): a dependency under a license not listed stops the build, on the pull request that changes `Cargo.lock` too. Before adding a license to both lists, read it and check that it is compatible with `GPL-3.0-or-later`.
